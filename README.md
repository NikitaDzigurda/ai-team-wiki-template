# ai-team-wiki-template

Шаблон общей базы знаний для команды и AI-помощников. Память хранится в Markdown и Git: люди и агенты используют одни и те же знания о проекте, решениях, договорённостях и завершённых задачах.

Внутри — пустые формы, CLI на Python, установщик инструкций, четыре skills и хуки для Claude Code и Codex. Сервер, база данных, API-ключи и платные сервисы для работы самой wiki не нужны. Этот шаблон не содержит истории, данных или архитектуры конкретного продукта.

## Как устроена работа

```text
repo-a/                         team-wiki/ — отдельный Git-репозиторий команды
├── AGENTS.md ──────────────►    ├── context/       общий контекст продукта
├── CLAUDE.md                    ├── standards/     общие соглашения
├── .agent-wiki.json             ├── projects/
├── .agents/skills/wiki-*        │   ├── repo-a/     память первого репозитория
├── .claude/skills/wiki-*        │   └── repo-b/     память второго репозитория
├── .codex/hooks.json            ├── scripts/       CLI, установщик, хуки
├── .claude/settings.json        └── templates/     инструкции и skills
└── .agent-wiki/ ────────────►    тот же team-wiki как Git-сабмодуль
```

Для каждой независимой команды создавайте **свою wiki из этого шаблона**. Несколько репозиториев одной команды подключаются к одной wiki с разными именами проектов. Не подключайте исходный репозиторий шаблона как рабочую память всех будущих команд.

В начале задачи агент читает компактные индексы и ищет релевантные записи. Во время работы сохраняет проверенное неочевидное знание. В конце записывает полезный итог и следующий шаг. Следующий участник продолжает с общего контекста, даже если использует другого помощника.

## Требования

- Git и Python **3.9+**. Зависимости Python устанавливать не нужно.
- Доступ всех участников к Git-репозиторию wiki и рабочим репозиториям.
- Любой помощник, умеющий читать Markdown и выполнять команды. Skills и хуки — дополнительные удобства; ручной протокол работает без них.

Примеры ниже используют `python3` в macOS/Linux. В Windows используйте доступную команду Python, например `python` или `py -3`. CLI и установщик проверяются CI на Linux, macOS и Windows; фактический запуск хуков зависит от оболочки и среды агента.

## Быстрый старт

### 1. Создайте wiki команды

В настройках этого GitHub-репозитория можно включить **Template repository**. Затем создайте из него отдельный репозиторий через **Use this template**, например `team-wiki`, и клонируйте его. Если шаблонный режим ещё не включён, достаточно перенести файлы в новый пустой репозиторий, исключив `.git`, `.idea` и другие локальные файлы.

```sh
git clone https://github.com/YOUR-TEAM/team-wiki.git
cd team-wiki
python3 scripts/validate.py
```

`YOUR-TEAM` и `team-wiki` — примеры: замените их своими значениями.

Перед подключением команды:

1. Заполните [context/product.md](context/product.md), [context/architecture.md](context/architecture.md) и [context/open-questions.md](context/open-questions.md). Пока сведений нет, оставьте явные заготовки.
2. Адаптируйте [standards/index.md](standards/index.md), особенно [правила Git](standards/global/git-commits.md), под команду.
3. При необходимости измените `default_branch` в [config.json](config.json). По умолчанию это `main`.
4. Проверьте и сохраните общие изменения в wiki через обычный Git по правилам команды.

Статус `proposal` в исходных документах означает заготовку или предложение. Меняйте его на `requirement`, `decision` или `fact` только при наличии соответствующего основания.

### 2. Подключите рабочий репозиторий

Выполняется из корня уже существующего Git-репозитория приложения:

```sh
cd path/to/your-project
git submodule add -b main https://github.com/YOUR-TEAM/team-wiki.git .agent-wiki
python3 .agent-wiki/scripts/install.py --project your-project
```

Используйте адрес **wiki своей команды**, а не исходного шаблона. Для другой ветки замените `main`. SSH URL тоже подходит. Авторизацию Git настройте обычным для команды способом; токены не добавляйте в файлы wiki или в URL репозитория.

`--project your-project` — имя памяти этого репозитория. Для другого репозитория задайте другое имя, например `service-api` или `web-client`. Без флага имя берётся из `origin`, а если его нет — из названия каталога. Для монорепозитория можно использовать одно имя памяти и описать модули внутри него.

### 3. Заполните память с помощью агента

Начните новую сессию в рабочем репозитории и отправьте:

> Выполни wiki-init: изучи репозиторий, заполни обзор, архитектуру и соглашения в командной wiki. Записывай только проверенное, неизвестное пометь явно. Затем выполни reindex и validate.

Если skills не распознаются, попросите агента открыть `AGENTS.md` и соответствующий `SKILL.md` в `.agents/skills/` или `.claude/skills/`. Формы также можно заполнить вручную в `.agent-wiki/projects/your-project/`.

### 4. Сохраните подключение и знания

Сначала проверьте diff. По правилам вашей команды сохраните память в отдельном репозитории wiki, затем её указатель и инструкции в приложении:

```sh
python3 .agent-wiki/scripts/wiki.py validate
python3 .agent-wiki/scripts/wiki.py sync -m "wiki(your-project): initial setup" --push

git add .gitmodules .agent-wiki .agent-wiki.json AGENTS.md CLAUDE.md .agents .claude .codex
git commit -m "chore: connect team wiki"
git push
```

Это команды для осознанного сохранения и публикации; установка сама их не запускает. Если использовали флаги отключения интеграций, исключите отсутствующие каталоги из `git add`.

`sync` включает только `projects/<текущий-проект>/`. Изменения в `context/`, `standards/` и инструментах нужно проверить и закоммитить отдельно. Если основная ветка защищена, используйте принятый в команде процесс с веткой и pull request.

### 5. Остальные участники

```sh
git clone --recurse-submodules <URL-РЕПОЗИТОРИЯ-ПРИЛОЖЕНИЯ>
cd <КАТАЛОГ-ПРИЛОЖЕНИЯ>
python3 .agent-wiki/scripts/install.py
```

Если приложение уже клонировано:

```sh
git submodule update --init --recursive
```

Сабмодуль фиксирует конкретный коммит wiki. Для свежей командной памяти используйте `wiki.py update`; после обновления сохраните изменившийся указатель сабмодуля вместе с изменениями приложения.

## Что делает установщик

`install.py`:

- создаёт `.agent-wiki.json` с именем проекта и относительным путём к wiki;
- создаёт `projects/<project>/` из пустого `projects/_template/`, если проекта ещё нет;
- добавляет или обновляет только блок `agent-wiki:start/end` в `AGENTS.md` и `CLAUDE.md`;
- добавляет свои хуки, сохраняя сторонние настройки и хуки;
- устанавливает `wiki-init`, `wiki-recall`, `wiki-save`, `wiki-session-end` в `.agents/skills/` и `.claude/skills/`.

Повторный запуск обновляет управляемые части и skills, сохраняя память проекта и текст вне маркеров. Локальные правки в установленных skills будут заменены: общие изменения вносите в `templates/skills/` wiki.

```sh
# Предварительный просмотр без записи файлов
python3 .agent-wiki/scripts/install.py --dry-run

# Только инструкции и skills для Codex
python3 .agent-wiki/scripts/install.py --no-claude

# Только Claude Code
python3 .agent-wiki/scripts/install.py --no-codex

# Инструкции и skills без автоматических хуков
python3 .agent-wiki/scripts/install.py --no-hooks

# Другая команда Python для сгенерированных команд
python .agent-wiki/scripts/install.py --python "py -3"
```

Флаги `--no-claude`, `--no-codex` и `--no-hooks` пропускают установку, но не удаляют ранее установленные файлы. Для отключения уже добавленного хука удалите его группу из настроек агента, сохранив сторонние группы.

### Работа без сабмодуля

Можно клонировать wiki рядом с приложением и выполнить установщик из корня приложения:

```sh
cd path/to/your-project
python3 ../team-wiki/scripts/install.py --project your-project
```

В конфиг будет записан относительный путь `../team-wiki`. Каждый участник должен создать такую же структуру каталогов. Git приложения в этом режиме не фиксирует версию wiki; синхронизация выполняется в отдельном клоне.

## Ежедневное использование

| Ситуация | Действие |
|---|---|
| Начало задачи | Прочитать индексы и вызвать `wiki-recall` |
| Новый проверенный факт или указание | `wiki-save`, обновляя существующую запись |
| Задача в несколько этапов | Создать `new-spec`, заполнить план и проверку |
| Решение между альтернативами | Создать `new-adr`, указать фактический статус |
| Изменение общего контракта | Обновить `context/` и связать с ADR |
| Завершение задачи | `wiki-session-end`, затем проверка и сохранение по правилам команды |

Примеры запросов агенту:

- «Найди в wiki, что уже известно о запуске тестов, и проверь актуальность».
- «Сохрани причину этого решения в ADR, а практическую ловушку — в gotchas».
- «Сохрани итог задачи и следующий шаг для другого участника».

## CLI

Команды ниже запускаются из рабочего репозитория. Создающие команды формируют заготовки: после них нужно заполнить тело документа.

```sh
python3 .agent-wiki/scripts/wiki.py where
python3 .agent-wiki/scripts/wiki.py recall "ключевые слова"
python3 .agent-wiki/scripts/wiki.py recall "слово" --all --full
python3 .agent-wiki/scripts/wiki.py new-memory local-runtime -t fact -d "Описание факта"
python3 .agent-wiki/scripts/wiki.py new-adr "Название решения" --slug chosen-approach
python3 .agent-wiki/scripts/wiki.py new-spec first-task -s "Цель задачи"
python3 .agent-wiki/scripts/wiki.py new-session first-task -s "Итог работы" --agent codex
python3 .agent-wiki/scripts/wiki.py reindex
python3 .agent-wiki/scripts/wiki.py validate
python3 .agent-wiki/scripts/wiki.py update
python3 .agent-wiki/scripts/wiki.py sync -m "wiki(your-project): update knowledge"
# Дополнительно опубликовать:
python3 .agent-wiki/scripts/wiki.py sync --push
```

Имя проекта определяется в порядке: глобальный флаг `--project`, переменная `AGENT_WIKI_PROJECT`, `.agent-wiki.json`, имя репозитория. Глобальный флаг ставится **перед командой**:

```sh
python3 scripts/wiki.py --project service-api recall "слово"
python3 scripts/wiki.py init service-api
```

`recall` — текстовый поиск, без embeddings и LLM. Все слова запроса должны присутствовать в документе. `--all` включает проекты, стандарты и общий контекст текущей wiki; `--full` показывает все совпавшие строки. Начните с короткого запроса.

`sync` проверяет wiki, создаёт локальный коммит файлов текущего проекта, затем при наличии `origin` выполняет `pull --rebase --autostash` в текущую ветку. Публикация происходит только с `--push`. При ошибке pull команда останавливается, локальный коммит сохраняется. Чужие подготовленные файлы, незавершённый merge/rebase и неоднозначный detached HEAD требуют ручного разрешения. При обычном detached HEAD сабмодуля команда переходит на `default_branch` без сброса истории. Вложения в папке проекта также входят в коммит: проверяйте их перед сохранением.

## Хуки и поддержка агентов

- **SessionStart** печатает индексы, ловушки и заголовки последних сессий в контекст.
- **Stop** один раз за сессию напоминает о памяти, если файлы приложения изменялись, а память нет. Это эвристика по Git и времени изменения файлов, а не проверка полноты записей.
- Хуки не вызывают модель, не записывают итог сами и не выполняют commit или push.
- При ошибке Python-хук пишет диагностику и выходит с кодом 0, чтобы не ломать работу агента. Если оболочка не смогла запустить Python, проверьте команду и пути.

Codex получает инструкции из `AGENTS.md`, skills устанавливаются в `.agents/skills/`. В локальном Codex проверьте хуки через `/hooks` и доверьте нужные определения. Формат и ограничения среды описаны в [официальной документации Codex](https://learn.chatgpt.com/docs/hooks). В облачной или управляемой среде локальные shell-хуки могут быть недоступны; тогда используйте протокол вручную.

Для Claude Code установщик создаёт `CLAUDE.md`, `.claude/skills/` и записи в `.claude/settings.json`. Хуки используют оболочку среды агента. В Windows проверьте её совместимость с командами в сгенерированном JSON; при необходимости используйте `--no-hooks` и ручное чтение индексов. Скрипты напрямую запускаются обычным Python.

Для любого другого помощника попросите прочитать `AGENTS.md` и следовать протоколу. Наличие файлов skills не гарантирует их автоматическое распознавание любым инструментом.

## Настройка

Общая конфигурация находится в [config.json](config.json), локальная привязка репозитория — в `.agent-wiki.json`.

| Ключ | По умолчанию | Назначение |
|---|---|---|
| `default_branch` | `main` | Ветка обновления wiki и выхода из detached HEAD |
| `submodule_path` | `.agent-wiki` | Резервный путь для хуков; установщик записывает фактический путь |
| `raw_base_url` | пусто | Необязательная база raw-ссылок для собственных интеграций; CLI не скачивает по ней документы |
| `index_max_lines` | `80` | Порог предупреждения о длине индекса |
| `session_start.recent_sessions` | `3` | Сколько итогов показать при старте |
| `session_start.include_*` | `true` | Включение стандартов, общего контекста и ловушек |
| `session_start.auto_update` | `false` | Автоматический fetch и fast-forward при старте; включается командой по желанию |
| `session_start.update_timeout` | `10` | Таймаут fetch в секундах |
| `stop_reminder` | `true` | Напоминание сохранить память |

Локально Stop можно отключить переменной окружения `AGENT_WIKI_STOP=off`. Общие файлы и заготовки написаны на русском; язык можно изменить в `standards/global/docs-style.md` и шаблонах.

## Проверка и сопровождение

Из корня wiki:

```sh
python3 scripts/validate.py
python3 -m unittest discover -s tests -v
```

Валидатор проверяет структуру, frontmatter, имена документов и относительные Markdown-ссылки, а в проектах и общем контексте — типовые шаблоны секретов. Он не доказывает фактическую точность записей и не обнаруживает все возможные секреты. Перед публикацией просматривайте diff и вложения.

Тесты работают только во временных каталогах: проверяют повторную установку, сохранение пользовательских инструкций и хуков, CLI, ошибки в ссылках, хуки, сабмодуль, локальный commit/push и отказ от захвата чужих staged-файлов. Сетевые сервисы и реальные репозитории команды не используются. [GitHub Actions](.github/workflows/validate.yml) повторяет проверки на трёх ОС.

После изменения шаблонов или инструментов в wiki обновите её в приложениях и повторно выполните `install.py`. Существующие документы проектов автоматически не переписываются. Обновления исходного template-репозитория не попадают в созданные из него репозитории автоматически: переносите нужные изменения отдельно.
